# Anna App Tool Starter

A minimal Anna App: one page, one button, and one Go Tool Executa. Click **Get backend data** to display sample values for `string`, `integer`, `number`, `boolean`, `array`, and `object`.

The frontend uses plain HTML, CSS, and JavaScript. The backend uses only the Go standard library. Cross-compile and package the binaries on your own computer.

## Run locally

Install Node.js 22+, Go 1.23+, and [uv](https://docs.astral.sh/uv/getting-started/installation/). The Anna CLI is pinned to `0.1.56` and installed with the npm dependencies. On the first run, uv downloads the Python development runtime required by that CLI version.

```bash
git clone https://github.com/wuyyyyyou/anna-app-tool-starter.git
cd anna-app-tool-starter
npm install
npm run dev
```

Open [http://localhost:5180/](http://localhost:5180/) and click **Get backend data**. Local development does not require an Anna login or an LLM API key.

If the port is already in use:

```bash
npm run dev -- --port 5181
```

Open the page through the Anna development environment or the Anna platform. Anna provides the SDK and tool ID mapping; opening the HTML file directly cannot invoke the backend.

## Sample data

| Field | Declared type | Default value |
| --- | --- | --- |
| `string_value` | `string` | `"Hello, Anna!"` |
| `integer_value` | `integer` | `42` |
| `number_value` | `number` | `3.14` |
| `boolean_value` | `boolean` | `true` |
| `array_value` | `array` with `string` items | `["Anna", "Go", "Executa"]` |
| `object_value` | `object` | `{"platform":"Anna","language":"Go"}` |

These are the six types Anna supports for tool parameters. The returned `data` is a regular JSON object. JavaScript represents both `integer` and `number` values as numbers; the type labels on the page reflect the tool's declarations. `null` is a valid JSON value, but it is not a separate parameter type in this example.

The button sends `args: {}`, so the tool uses the defaults declared in its protocol manifest. Callers can override any sample field. The tool validates argument types, array items, and unknown arguments. Explicit `false`, `0`, empty arrays, and empty objects are preserved.

```bash
npm run tool:describe
npm run tool:invoke
npm run tool:invoke -- --args '{"boolean_value":false,"integer_value":0}'
```

## Configuration and protocol

```text
app.json                         App metadata and bundled Executa paths
manifest.json                    App UI, dependencies, and Host API permissions
bundle/
  index.html / app.js / app.css   Static frontend, no build step
  anna-tool-ids.js                Generated by the CLI, ignored by Git
executas/type-demo/
  executa.json                    Local command and binary distribution settings
  manifest.json                  Protocol manifest returned by describe
  main.go                        stdio JSON-RPC + get_types
  main_test.go                   Arguments, responses, error recovery, and framing tests
  dist/                          Locally built binary archives, ignored by Git
scripts/
  build-binary.go                 Cross-compilation, packaging, SHA-256, and smoke checks
  check.mjs                      Configuration, App, tool, and packaged binary checks
```

The tool's protocol manifest is embedded in the executable using `go:embed`, and `describe` returns it directly. The distribution manifest at the archive root is generated by the build script and defines the entrypoint and file permissions. These two manifests serve different purposes.

The same handle connects the App to its tool:

```text
app.json: bundled_executas["type-demo"].path
    → executas/type-demo
App manifest: bundled:type-demo
UI permission: required:bundled:type-demo
Frontend ID: window.__ANNA_TOOL_IDS__["type-demo"]
```

The `tool-dev-type-demo` ID in `executa.json` is only for local development. During publishing, the Anna CLI obtains a server-generated `tool_id`, resolves bundled references, and generates the frontend mapping. Use that mapping instead of hard-coding a production tool ID.

The frontend calls `anna.tools.invoke({tool_id, method: "get_types", args: {}})`. The tool reads `params.tool` and `params.arguments`. A successful JSON-RPC response looks like this:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "success": true,
    "data": {
      "string_value": "Hello, Anna!",
      "integer_value": 42,
      "number_value": 3.14,
      "boolean_value": true,
      "array_value": ["Anna", "Go", "Executa"],
      "object_value": {"platform": "Anna", "language": "Go"}
    },
    "tool": "get_types"
  }
}
```

The SDK returns the business `data` payload and handles the protocol envelope. The frontend does not construct the tool's JSON-RPC frames or unwrap its responses. For `describe`, `result` must contain the manifest directly, without the `success`/`data` wrapper.

The tool supports `initialize`, `describe`, `invoke`, and `health`. It keeps reading stdin until EOF, writes one JSON-RPC frame per line to stdout, and sends logs to stderr. This example requires no credentials or host capabilities.

## Build binaries locally

Build for your current platform and generate an archive with a `.sha256` checksum:

```bash
npm run build
```

Cross-compile all supported platforms:

```bash
npm run build:all
```

Build one specific platform:

```bash
npm run build -- --platform linux-x86_64
```

| Anna platform key | Go GOOS / GOARCH | Archive format |
| --- | --- | --- |
| `darwin-arm64` | `darwin / arm64` | `.tar.gz` |
| `darwin-x86_64` | `darwin / amd64` | `.tar.gz` |
| `windows-x86_64` | `windows / amd64` | `.zip` |
| `linux-x86_64` | `linux / amd64` | `.tar.gz` |
| `linux-aarch64` | `linux / arm64` | `.tar.gz` |

All targets use `CGO_ENABLED=0`. The installed tool binary does not require Go, Node.js, or additional dynamic libraries on the target machine. Archives are written to `executas/type-demo/dist/type-demo-v0.1.0-<platform>.<format>`.

Each archive contains:

```text
manifest.json          Distribution manifest: version, runtime.binary.entrypoint, permissions
bin/type-demo          macOS / Linux executable
# Windows uses bin/type-demo.exe
```

Keep the tool versions in `executa.json`, the protocol manifest, and the App's `min_version` in sync. The App version can change independently. Rebuild the binaries after changing the embedded manifest.

## Validate

```bash
npm run check
npm run check -- --all
```

The checks cover configuration consistency, Go argument and protocol tests, `anna-app validate --strict`, and the packaged archives.

For the current platform, the check extracts and runs the executable from the final archive. It keeps stdin open while checking initialization, `describe`, defaults, invalid arguments, custom values, unknown methods, error recovery, health, and shutdown at EOF.

`--all` also cross-compiles the other platforms and checks their archive structure and contents. Binaries for other operating systems and architectures still need execution checks in their respective environments.

## Publish to Anna

Build every platform declared in `binary_artifacts`, then use the CLI to upload your own version:

```bash
npx anna-app login --host https://staging.anna.partners
npx anna-app account set-handle YOUR_HANDLE
npm run build:all
npx anna-app apps push
npx anna-app apps cut 0.1.0
npx anna-app apps release 0.1.0
```

`apps push` updates the working draft. `apps cut` uploads the local binaries and freezes the tool dependencies. `apps release` publishes that version. The binaries are uploaded directly to Anna storage, so publishing does not require GitHub Actions or public download URLs. To list the App in the store, provide the required listing assets and submit it for review.

Anna identity caches (`.anna/`), generated tool ID mappings, binary artifacts, and private environment files are excluded from Git. The local `docs/` directory contains article drafts and is also excluded.
